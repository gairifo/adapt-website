AI & Migration

How AI-Assisted Migration Actually Works (And Why Just Asking an LLM Falls Short)

AI Migration 2026-10-26 6 min read

Every conversation about legacy migration eventually arrives at the same question: can't we just use AI to do this? The short answer is yes — with caveats that most vendors won't tell you upfront. AI is genuinely useful for migration. The problem is the gap between how it's marketed and how it actually works when production code is involved. That gap is where failed migration projects happen.

This article explains what the empirical evidence shows about naive AI code conversion, what a disciplined AI-assisted migration process actually looks like, and where the real limits are. It's written for CTOs and VPs of Engineering evaluating vendors who claim to "use AI to migrate your systems."

What the Evidence Shows: When You Just Feed Code to an LLM

One of the more rigorous public tests of naive LLM-based migration involved a production SAS script containing 143 insurance-code mappings. The developer fed the code to a leading LLM and asked for a migration to another platform. The output looked correct — it compiled, it was structurally plausible, it read like real migration output. The value accuracy was 28.6%.

That number deserves to sink in. Nearly three in four mapped values were wrong, in code that looked right. In a standard code review, these errors would be easy to miss because the structure was valid and the output was fluent. In production, they would surface as incorrect business results — misrouted records, wrong premium calculations, invalid claim classifications.

The accuracy degraded sharply with scale. For mapping tables under 20 clauses, LLM accuracy ran between 80% and 90%. For tables over 100 clauses — the kind that actually appear in production insurance, financial, and healthcare systems — accuracy dropped to 25–30%. The applications that most need AI-assisted migration are precisely the ones where naive LLM conversion fails most badly.

Setting the model temperature to zero — a configuration often cited as guaranteeing deterministic output — did not prevent different outputs across identical runs. Prompt tuning helped at the margins but plateaued. The failure was architectural, not a matter of finding the right prompt.

The Three Failure Modes of Naive AI Code Conversion

From documented migration projects and independent analysis, three failure patterns recur consistently when LLMs are used without a surrounding engineering structure.

Truncation of large artifacts. LLMs operate within context limits. A legacy codebase with hundreds of mapping rules, configuration constants, or state machine definitions will exceed what a model holds in active attention. When this happens, the model doesn't stop and declare the problem — it quietly truncates or approximates. The output is shorter than the source, internally consistent, and missing critical logic. This failure mode is insidious because it produces fewer lines of code, which can look like simplification rather than omission.

Plausible invention. LLMs are trained to produce fluent, coherent output. When they lack sufficient context to generate a correct value or rule, they generate something plausible — a value that looks like the right format, a rule that matches the general pattern of the surrounding code. In a migration context, plausible-but-wrong business logic is more dangerous than obvious errors: it passes structural review and fails in production, often on edge cases that appear only under specific conditions.

Loss of stateful logic. Legacy applications frequently carry significant stateful behavior: retained variables, session-level tracking, global counters, group-level processing sequences, and side effects embedded in execution flow. This logic is easy for a model to miss because it's implicit in the source language's execution model — not explicitly declared in the way modern frameworks express state. A model that doesn't carry that execution model in its understanding will produce output that's behaviorally different from the original, often in ways that pass unit tests but fail integration tests.

What Structured AI-Assisted Migration Actually Looks Like

The architecture that produces reliable results at scale separates the work according to what each component is genuinely capable of. This is the core insight: AI and deterministic systems have different strengths, and confusing one for the other is the most common failure in naive AI migration approaches.

Deterministic extraction handles exactness. The parts of a legacy system that require precise value mapping — lookup tables, routing rules, configuration constants, data type conversions — are handled by deterministic processes that read verified client-owned inputs with full fidelity: database schemas and their data, stored procedures and PL/SQL logic, API contracts, documented business rules. An LLM doesn't touch these values directly. They're extracted into a structured intermediate representation that can be validated and audited.

AI handles semantic reasoning. Architecture design, naming, domain model translation, and processing flow — the parts where understanding intent matters more than precise value mapping — are where LLMs contribute genuine value. A senior architect defines the target structure; the AI assists with generating idiomatic code from the structured intermediate. The LLM is doing what it's good at: reasoning about meaning and generating coherent output from well-specified inputs.

Traceability closes the loop. Every generated artifact links back to a specific source input — a field in a database schema, a line in a stored procedure, a clause in a documented API contract, an observed behavior recorded in a walkthrough of the running application. Traceability is the anti-hallucination mechanism. If generated output can't be traced to a verified source, it's flagged for human review rather than committed. This structural check is what distinguishes AI-assisted migration from AI-generated code you have to hope is correct.

Thoughtworks, in a documented AI-assisted migration project, found that a 10-sport program that would have taken two to three years using traditional methods completed in three to four weeks of total effort. Per-module onboarding dropped from 10–15 weeks to under a day. These results came from a disciplined process: source traceability, confidence markers on extracted artifacts, SME review for ambiguous cases, and structured specs that fed code generation rather than free-form prompting.

The Role of Human Architects — and Why It Doesn't Go Away

AI-assisted migration that actually works is not autonomous. The timeline compression — which in practice runs 3–5× versus a traditional manual rewrite — comes from eliminating the mechanical generation work, not from removing architectural judgment. Those are different things, and conflating them is how migration projects get into trouble.

In Adapt's migration factory, senior architects own all structural decisions: how the target architecture is organised, how the legacy domain model maps to modern constructs, where accumulated technical debt should be resolved versus preserved to match legacy behavior. The AI component accelerates generation; architects control the design.

In regulated industries — financial services, healthcare, government — engineer review, execution, and sign-off remain mandatory regardless of how much AI is involved in the generation process. What changes is the ratio of review to mechanical work. One migration practitioner documented that per-script effort dropped from 5–8 days of manual work to a few hours of review when a disciplined AI-assisted process was applied. The work that remains is the work that requires human judgment. The work that was eliminated was the work that required only human time.

What Can and Can't Be Automated

It's worth being direct about the limits. Overpromising on AI migration has set back the field by producing failed projects — and failing projects have a cost beyond the immediate budget: they make the next attempt harder to justify internally.

The parts of migration that AI handles reliably in a structured process include: schema conversion and data type mapping, routing logic with clear source artifacts, standard CRUD patterns, API interface generation from existing contracts, test scaffolding from documented and observed behavior. These are the high-volume, pattern-driven components that dominate a typical legacy codebase.

The parts that require careful handling: business rules encoded in application behavior that was never documented; event-driven logic with complex state interactions; exceptions that appear only under specific load or data conditions; integration behavior that depends on runtime configuration rather than code.

The parts that cannot be automated without direct SME input: intent behind code that was written one way but executed differently because of environmental factors; logic where the correct behavior is a business judgment rather than an engineering fact; requirements that exist only in the institutional knowledge of long-tenured maintainers who may no longer be available.

This last category is why the quality of the starting inputs matters as much as the AI tooling. Migrations that produce reliable outputs start from accurate, complete inputs: the database schemas that capture the data model, the stored procedures and business logic that capture the application's rules, the API contracts that define its interfaces, and behavioral walkthroughs of the running system that capture what it actually does under real conditions. The AI-assisted factory is only as good as the inputs it works from.

The Questions Worth Asking Any Vendor

If you're evaluating vendors who claim AI-assisted migration capabilities, a few questions distinguish disciplined processes from marketing:

What is the verification method? How does the vendor confirm that generated code matches the behavior of the original? "We review it" is a different answer from "we test it against documented behavior using a defined equivalence framework." Ask for specifics.

How is business logic captured, and what are the inputs? A process that works from client-owned artifacts — schemas, stored procedures, documented behavior — is structured differently from one that reads the running application and makes inferences. Both can produce results; they have very different accuracy and auditability profiles.

Who makes architectural decisions, and at what stage? AI-assisted migration that works has architects defining structure before generation begins. A process where architecture is implied by what the AI produces is a different proposition.

What happens with the parts that can't be automated? How are ambiguous or undocumented logic paths handled? Is there a defined escalation path for cases where the AI can't produce a verifiable output? The answer tells you something about whether the process has been tested against real legacy codebases or designed for idealized ones.

The organisations that evaluate migration vendors rigorously before committing consistently report better outcomes than those that evaluate on the basis of timeline promises alone.
